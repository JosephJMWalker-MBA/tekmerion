# Finalized Record Invariants

This document defines the behavior required when a Tekmerion draft is added to the permanent record. These rules are product policy and must be enforced by repositories, persistence tests, export tests, and—where practical—database constraints.

## Vocabulary

- **Draft:** A mutable `RecordEntry` that has not been added to the permanent record.
- **Finalized record:** A `RecordEntry` with `state = finalized` and a non-null `finalized_at`.
- **Correction:** A new finalized record with `record_type = correction` and `corrects_record_entry_id` referencing an earlier finalized record.
- **Canonical payload:** A deterministic, versioned serialization of the fields whose integrity Tekmerion protects.
- **Evidence original:** The preserved original bytes captured or imported into Tekmerion.
- **Derivative:** A separate asset produced from an original, such as a thumbnail, crop, annotation, OCR rendering, or redacted copy.

## State transitions

Permitted:

```text
draft → finalized
finalized → corrected (display/status projection only)
draft → deleted
```

Not permitted:

```text
finalized → draft
finalized → deleted in place
finalized → silently modified
correction → overwrite original
```

A finalized record may be projected as `corrected` after a valid correction is added, but the original row and canonical payload remain unchanged.

## Finalization preconditions

A draft may be finalized only when:

1. `id`, `workspace_id`, `agreement_id`, `record_type`, `title`, `factual_description`, `occurred_at`, `recorded_at`, `timezone`, and `created_by_party_id` are present.
2. `recorded_at` was generated by Tekmerion and is not user-supplied.
3. `occurred_at` is explicitly confirmed by the user.
4. Every linked evidence asset exists in managed storage.
5. Every linked evidence asset has a stored SHA-256 hash calculated from its preserved bytes.
6. Every contractual obligation link has clause provenance or an explicit provenance-unavailable reason.
7. The final review screen has been displayed and the user has selected **Add to Record**.

## Canonical payload version 1

The v1 canonical payload includes exactly these logical fields in a stable order:

```text
schema_version
record_id
workspace_id
agreement_id
agreement_version_id
obligation_id
source_clause_id
record_type
title
factual_description
interpretation_text
occurred_at
recorded_at
timezone
location_data
created_by_party_id
corrects_record_entry_id
finalized_at
evidence[]:
  evidence_id
  relationship_type
  sha256
  asset_role
  capture_method
```

Rules:

- UTF-8 encoding.
- Unicode normalized to NFC.
- Object keys ordered lexicographically in serialized JSON.
- Arrays ordered by explicit `display_order`, then stable UUID.
- Timestamps serialized as RFC 3339 UTC values while preserving the original timezone in a separate field.
- Null is distinct from an empty string.
- No transient UI, database row-version, local file path, or derived status field is included.
- Canonicalization version is stored with the resulting hash.

## Finalization transaction

Finalization must occur as one recoverable operation:

1. verify preconditions;
2. durably verify evidence files and hashes;
3. set `finalized_at` using the system clock;
4. build canonical payload;
5. calculate `record_hash`;
6. load the preceding agreement-chain hash, if any;
7. calculate `chain_hash`;
8. attempt device signature;
9. persist immutable finalized metadata and evidence links;
10. commit the transaction;
11. schedule any deterministic status/reminder projections after commit.

If persistence fails before commit, the record remains a draft and no partial finalized record may appear in the timeline.

If device signing fails, finalization may continue only when:

- hash and chain values were created successfully;
- the signature state is recorded as unavailable or failed;
- the user is not told that the record is signed.

## Mutation prohibition

After finalization, repository APIs must reject changes to:

- title;
- factual description;
- interpretation text;
- occurred-at;
- recorded-at;
- timezone;
- location data;
- agreement/version/obligation/clause links;
- created-by party;
- evidence links;
- correction target;
- finalization timestamp;
- canonicalization version;
- record hash;
- chain hashes;
- signature metadata.

Permitted post-finalization projections that do not mutate the canonical record:

- cached display labels;
- search-index entries;
- timeline grouping;
- verification results generated later;
- a projection that the record has been corrected;
- export inclusion/exclusion choices.

## Correction behavior

A correction must:

1. be a new draft and receive a new UUID;
2. reference exactly one finalized record through `corrects_record_entry_id`;
3. explain the corrected fact or interpretation in its own finalized content;
4. preserve the original record and all original evidence links;
5. optionally link new evidence without replacing old evidence;
6. receive its own `record_hash`, `chain_hash`, finalization time, and signature state;
7. appear after the corrected record in chain order;
8. render with a visible relationship to the original in timeline and export.

A correction does not erase the original, even when the original contains an error.

Corrections may themselves be corrected through a new linked correction. The export must preserve the full correction graph and identify the latest correction without hiding prior nodes.

## Evidence rules

1. An original evidence asset is immutable after ingestion.
2. Metadata extraction must not rewrite the original.
3. A derivative is a new `EvidenceAsset` with its own UUID and SHA-256.
4. A derivative must reference its original through `derived_from_evidence_id`.
5. Removing a local thumbnail must not remove the original.
6. An evidence link included in a finalized record cannot be deleted in place.
7. A later record may explain that evidence is irrelevant, mistaken, incomplete, or disputed.
8. Externally imported evidence must retain `pre_ingestion_history_unknown` semantics.

## Deletion and privacy

V1 must not silently destroy finalized evidence.

If a user requests removal of a finalized agreement record from the active app:

- Tekmerion first offers a full Record Package export;
- the destructive action requires explicit confirmation;
- the action creates a local destruction receipt containing IDs and hashes but not necessarily private content;
- the app must not claim an append-only record survives deliberate device-level deletion;
- backup copies and prior exports remain outside Tekmerion's control.

A future privacy/deletion ADR must reconcile personal data rights with integrity claims before cloud synchronization exists.

## Required repository tests

### Finalization

- A valid draft finalizes successfully.
- A draft with missing required fields cannot finalize.
- A draft with missing evidence bytes cannot finalize.
- A failed transaction leaves the draft mutable and no finalized projection visible.

### Immutability

- Updating each protected field after finalization is rejected.
- Replacing or removing a finalized evidence link is rejected.
- Reopening a finalized record as a draft is rejected.

### Correction

- A correction receives a new UUID.
- A correction cannot target a draft.
- A correction preserves the original canonical payload and evidence.
- Multiple corrections preserve the full graph.

### Integrity

- Canonicalizing the same logical payload twice produces identical bytes and hash.
- Changing one protected value changes `record_hash`.
- Changing one evidence byte causes evidence verification failure.
- Reordering records causes chain verification failure.
- Signature verification fails after payload mutation.
- Hash verification remains possible when the signing key is unavailable.

### Export

- Export distinguishes `occurred_at`, `recorded_at`, and `finalized_at`.
- Export includes canonicalization version and hashes.
- Export shows correction relationships without replacing originals.
- Selective export declares that chain verification applies only to included scope when the full chain is absent.

## User-facing language

At finalization:

> Adding this entry to the Record preserves its current contents. Later changes are added as corrections rather than replacing this entry.

For in-app evidence after successful verification:

> Verified unchanged since capture into Tekmerion.

For imported evidence after successful verification:

> Verified unchanged since import into Tekmerion. Its history before import is unknown.

Never display:

- “Legally proven.”
- “Guaranteed authentic.”
- “Court admissible.”
- “Impossible to alter.”
